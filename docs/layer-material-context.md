# Material-derived layer preview context

The variable-layer preview now resolves every material slot and derives one plate-wide shrinkage compensation. It uses the active plate's visible printable object groups, not only the selected object. Catalog reads are deduplicated by preset ID, restored to slot order and aborted when the dialog closes. The dialog disables edits while resolving, and reports failed or incomplete reads instead of showing first-filament estimates. Embedded native vectors take precedence over displayed first-slot settings. Already accepted process corrections are applied to the same context.

Pinned OrcaSlicer 2.4.2 source (`8500fcdccaa10b5099ac20d252af3a7c560046f1`) establishes the following:

- `Print.cpp:451–545` collects region materials, model-volume base/paint materials, every positive height-range base assignment, support materials and the explicit tower material. Region keys retain the `PrintObject.cpp:3664` scope/feature precedence. Modifier regions use overlapping XYZ bounds, including range-clipped triangle bounds and the native union of modifier/ancestor bounds (`PrintApply.cpp:878,957`). Negative/support-volume base assignments do not contribute (`Model.cpp:2536`).
- `PrintRegion.cpp:71` gates feature materials by walls, print-wide brim, infill and shell counts. Support, raft or enforced-support configuration collects both support slots even if a support interface will ultimately have no paths (`Print.hpp:429`, `Print.cpp:489`). Tower use retains the source's pre-deduplication material-count gate, wrapping/timelapse/spiral conditions and selected-plate spiral override.
- `Print.hpp:942` declares `extruders(bool conside_custom_gcode = false)`. Shrinkage calls the default, so custom layer ToolChange events do **not** add compensation participants.
- `Print.cpp:3851–3890` requires exact equality of both XY and Z shrinkage percentages across used slots. If either differs, all three compensation axes become one. Otherwise XY/Z are `100 / percentage`. Short native vectors fall back to their first entry (`Config.hpp:624`); absent settings use native defaults.

This includes declared possible materials before slicing. A configured modifier or a positive height-range extruder can count even when the final toolpath uses none of it. The UI states which slots it used. Bounded facet decoding, 20,000 region work units and four million triangle/range visits prevent unbounded analysis; unsupported or malformed contexts fail visibly.

## Observed installed CLI discrepancy

**The source-derived preview matches a newly captured installed-native GUI case; the fresh-load CLI differs.** On a fresh process, installed OrcaSlicer 2.4.2 accepted XY98%/Z98% (confirmed in exported G-code) yet sliced a 20 mm cube into 100 layers ending at Z20. The source-derived schedule has 102 layers. This was reproduced with embedded two-slot native 3MF, with a single explicitly loaded filament, and using both STL and 3MF plus `--load-settings` / `--load-filaments`. The explicit-profile probe used bundled `Prusa MK4 0.4 nozzle`, `0.20mm Standard @MK4`, and `Prusa Generic PLA @MK4`, with isolated `--datadir`/working/output directories. Changing the unused slot from XY97% to XY98% leaves every native motion unchanged.

The preview shows a clear discrepancy warning whenever it computes non-unity compensation. It does not pre-scale geometry or change slicing settings. On 2026-09-27 the desktop was accessible: the same 20 mm, one-material XY98%/Z98%, 0.2 mm-layer project was opened, sliced and exported through the installed native GUI. It produced **102 layers through Z20.4**, matching the source-derived preview schedule. The checked-in GUI input and G-code provide a reproducible positive reference; this single cube does not establish every shrinkage/material combination. A plausible source explanation is that `PrintApply.cpp:1534` computes transformed instances before installing fresh `m_objects` at line 1593; later slicing parameters are refreshed at line 1776. That explanation is an inference, not a proven complete root cause.

Validation: 10 new unit/client tests and 47 existing variable-layer/texture/brush tests pass. Five installed-native tests pass: one locks the observed discrepancy as explicit diagnostic evidence; four compare mixed-XY/equal-Z part, paint, height-range and support cases with neutral-compensation reference toolpaths (17,723 / 15,918 / 8,890 / 8,869 motions). Those negatives do not prove that positive compensation works in the CLI. All three browser tests pass (9.5 s): full embedded vectors; delayed/deduplicated catalog reads; unavailable material and cancellation. Catalog tests create/delete their own compatible custom filament. One additional fixture test compares every source-derived Z to the captured GUI output.
